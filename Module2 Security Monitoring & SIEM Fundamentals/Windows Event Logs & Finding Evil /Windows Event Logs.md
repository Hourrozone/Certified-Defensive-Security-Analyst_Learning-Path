# 🪟 Windows Event Logs

---

## 📚 Windows Event Logging Basics

Windows Event Logs are an essential part of the Windows Operating System. They store logs generated by different components of the system, including the operating system itself, applications, ETW providers, services, and other components.

Windows event logging provides comprehensive information about **application errors, security events, and diagnostic activities**. As cybersecurity professionals, we rely heavily on these logs for security analysis, troubleshooting, threat detection, and intrusion detection.

The logs are categorized into different event logs, such as **"Application"**, **"System"**, **"Security"**, and others. This categorization helps organize events based on their source or purpose.

Windows Event Logs can be accessed using the **Event Viewer** application or programmatically through APIs such as the **Windows Event Log API**.

Accessing the Windows Event Viewer as an administrative user allows us to explore the various logs available on the system.

### 📂 Default Windows Event Logs

The default Windows event logs consist of:

* **Application** — Contains events related to applications and application errors.
* **Security** — Contains security-related events such as successful and failed logons.
* **Setup** — Contains events related to system setup and installation activities.
* **System** — Contains general information and events generated by Windows system components.
* **Forwarded Events** — Contains event log data forwarded from other machines.

The **"Forwarded Events"** section is different from the other logs because it contains events collected from other machines. This centralized logging capability is particularly useful for system administrators and security teams who want to view events from multiple systems in one location.

In our current analysis, however, we focus on event logs from a **single machine**.

> 📝 **Note:** The Windows Event Viewer can also open and display previously saved `.evtx` files. These files can then be found in the **"Saved Logs"** section.

## 🧩 The Anatomy of an Event Log

When examining **Application** logs, we encounter two distinct levels of events: **Information** and **Error**.

<img width="342" height="92" alt="image" src="https://github.com/user-attachments/assets/4b6b7429-caae-444a-8626-e7d664fc66f2" />

**Information** events provide general usage details about an application, such as when the application starts or stops.

On the other hand, **Error** events highlight specific problems and often provide detailed information about what went wrong.

<img width="1000" height="665" alt="image" src="https://github.com/user-attachments/assets/2ad35b31-3520-4daf-bdf2-e6ba894edf62" />

Each entry in the Windows Event Log is an **"Event"** and contains several primary components:

| Component         | Description                                                                                                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Log Name**      | The name of the event log, such as Application, System, Security, etc.                                                                                                                  |
| **Source**        | The software that logged the event.                                                                                                                                                     |
| **Event ID**      | A unique identifier for the event.                                                                                                                                                      |
| **Task Category** | A value or name that can help us understand the purpose or use of the event.                                                                                                            |
| **Level**         | The severity of the event, such as Information, Warning, Error, Critical, and Verbose.                                                                                                  |
| **Keywords**      | Flags that allow us to categorize events beyond the other classification options. These are generally broad categories, such as "Audit Success" or "Audit Failure" in the Security log. |
| **User**          | The user account that was logged on when the event occurred.                                                                                                                            |
| **OpCode**        | Identifies the specific operation that the event reports.                                                                                                                               |
| **Logged**        | The date and time when the event was logged.                                                                                                                                            |
| **Computer**      | The name of the computer where the event occurred.                                                                                                                                      |
| **XML Data**      | Contains all the above information in XML format along with additional event data.                                                                                                      |

### 🏷️ Why the Keywords Field Matters

The **Keywords** field is particularly useful when filtering event logs for specific types of events.

It can improve the precision of search queries by allowing us to specify the types of events we are interested in. This makes log management and analysis more efficient.

## 🔐 Security Logs and Event ID 4624

Switching our focus to **Security logs**, let's consider **Event ID 4624**, which is a commonly occurring event.

[Microsoft Event ID 4624 documentation](https://docs.microsoft.com/en-us/windows/security/threat-protection/auditing/event-4624?utm_source=chatgpt.com)

<img width="1000" height="644" alt="image" src="https://github.com/user-attachments/assets/38eaf8b2-1d67-4206-aa18-36dc178997bc" />

According to Microsoft's documentation, Event ID `4624` indicates the creation of a **logon session on the destination machine**, originating from the accessed computer where the session was established.

Within this event, we can find several important details.

One of these is the **"Logon ID"**, which can be used to correlate this logon with other events that contain the same **Logon ID**.

Another important field is **"Logon Type"**, which tells us what type of logon occurred.

In this example, the Logon Type indicates a **Service** logon. This suggests that **"SYSTEM"** initiated a new service.

However, we still need additional investigation to determine exactly which service was involved. We can do this by correlating the event with other events and using information such as the **Logon ID**.

## 🔎 Leveraging Custom XML Queries

To streamline our analysis, we can create **custom XML queries** to identify related events.

One useful starting point is the **Logon ID**. By using it to search for related events, we can build a clearer picture of what happened around a particular logon.

In Windows Event Viewer, navigate to:

**"Filter Current Log" → "XML" → "Edit Query Manually"**

This provides access to a custom XML query language that allows us to perform more granular searches within the event logs.

<img width="1000" height="670" alt="image" src="https://github.com/user-attachments/assets/9f08c1f3-cabc-4e48-a928-802683664090" />

In the example query, we focus on events containing the **"SubjectLogonId"** field with a value of **"0x3E7"**.

The reason for selecting this value is that we want to correlate events associated with a specific **Logon ID** and understand what other activities occurred under that same logon session.

<img width="1000" height="685" alt="image" src="https://github.com/user-attachments/assets/7817fec7-eb66-41f9-8e0f-961c5ff61a55" />

> 💡 **Tip:** If assistance is required when creating the query, automatic filters can be enabled. We can then explore how the selected filters affect the XML representation of the query.

For further guidance, Microsoft also provides informative articles about advanced XML filtering in Windows Event Viewer.

By constructing queries like this, we can narrow our focus to the account responsible for initiating the service and eliminate unnecessary information.

This approach helps us build a clearer picture of recent logon activities associated with the specified **Logon ID**.

However, even after filtering the events, the amount of data can still be significant.

Within the event description, we find valuable information, such as:

### 🔐 Understanding SACL

If you are unfamiliar with **SACL**, the provided Microsoft documentation on access control lists (ACLs) can help explain the concept.

[Microsoft Access Control Lists documentation](https://docs.microsoft.com/en-us/windows/win32/secauthz/access-control-lists?utm_source=chatgpt.com)

The **"S"** in **SACL** stands for **System Access Control List**.

A SACL allows administrators to configure auditing for access attempts against secured objects.

Each **Access Control Entry (ACE)** in a SACL specifies which types of access attempts by a particular trustee should generate records in the security event log.

Depending on the configuration, ACEs in a SACL can generate audit records for:

* Failed access attempts
* Successful access attempts
* Both failed and successful access attempts

For more information about SACLs, see **Audit Generation and SACL Access Right**.

Based on this information, it becomes apparent that the permissions of a file were altered to modify the logging or auditing of access attempts.

Further examination of the event details reveals additional interesting information.

This indicates a potential setup process, although it is important to remember that malware can sometimes masquerade under legitimate process names.

# 📋 Useful Windows Event Logs

---

## 🖥️ Windows System Logs

| Event ID                                     | Description                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1074 — System Shutdown/Restart**           | This event log indicates when and why the system was shut down or restarted. By monitoring these events, you can determine if there are unexpected shutdowns or restarts, potentially revealing malicious activity such as malware infection or unauthorized user access.                                             |
| **6005 — The Event log service was started** | This event log marks the time when the Event Log Service was started. This is an important record, as it can signify a system boot-up, providing a starting point for investigating system performance or potential security incidents around that period. It can also be used to detect unauthorized system reboots. |
| **6006 — The Event log service was stopped** | This event log signifies the moment when the Event Log Service was stopped. It is typically seen when the system is shutting down. Abnormal or unexpected occurrences of this event could point to intentional service disruption for covering illicit activities.                                                    |
| **6013 — Windows uptime**                    | This event occurs once a day and shows the uptime of the system in seconds. A shorter than expected uptime could mean the system has been rebooted, which could signify a potential intrusion or unauthorized activities on the system.                                                                               |
| **7040 — Service status change**             | This event indicates a change in service startup type, which could be from manual to automatic or vice versa. If a crucial service's startup type is changed, it could be a sign of system tampering.                                                                                                                 |

## 🔐 Windows Security Logs

| Event ID                                                                                          | Description                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1102 — The audit log was cleared**                                                              | Clearing the audit log is often a sign of an attempt to remove evidence of an intrusion or malicious activity.                                                                                                                              |
| **1116 — Antivirus malware detection**                                                            | This event is particularly important because it logs when Defender detects a malware. A surge in these events could indicate a targeted attack or widespread malware infection.                                                             |
| **1118 — Antivirus remediation activity has started**                                             | This event signifies that Defender has begun the process of removing or quarantining detected malware. It's important to monitor these events to ensure that remediation activities are successful.                                         |
| **1119 — Antivirus remediation activity has succeeded**                                           | This event signifies that the remediation process for detected malware has been successful. Regular monitoring of these events will help ensure that identified threats are effectively neutralized.                                        |
| **1120 — Antivirus remediation activity has failed**                                              | This event is the counterpart to 1119 and indicates that the remediation process has failed. These events should be closely monitored and addressed immediately to ensure threats are effectively neutralized.                              |
| **4624 — Successful Logon**                                                                       | This event records successful logon events. This information is vital for establishing normal user behavior. Abnormal behavior, such as logon attempts at odd hours or from different locations, could signify a potential security threat. |
| **4625 — Failed Logon**                                                                           | This event logs failed logon attempts. Multiple failed logon attempts could signify a brute-force attack in progress.                                                                                                                       |
| **4648 — A logon was attempted using explicit credentials**                                       | This event is triggered when a user logs on with explicit credentials to run a program. Anomalies in these logon events could indicate lateral movement within a network, which is a common technique used by attackers.                    |
| **4656 — A handle to an object was requested**                                                    | This event is triggered when a handle to an object (like a file, registry key, or process) is requested. This can be a useful event for detecting attempts to access sensitive resources.                                                   |
| **4672 — Special Privileges Assigned to a New Logon**                                             | This event is logged whenever an account logs on with super user privileges. Tracking these events helps to ensure that super user privileges are not being abused or used maliciously.                                                     |
| **4698 — A scheduled task was created**                                                           | This event is triggered when a scheduled task is created. Monitoring this event can help you detect persistence mechanisms, as attackers often use scheduled tasks to maintain access and run malicious code.                               |
| **4700 & 4701 — A scheduled task was enabled/disabled**                                           | This records the enabling or disabling of a scheduled task. Scheduled tasks are often manipulated by attackers for persistence or to run malicious code, thus these logs can provide valuable insight into suspicious activities.           |
| **4702 — A scheduled task was updated**                                                           | Similar to 4698, this event is triggered when a scheduled task is updated. Monitoring these updates can help detect changes that may signify malicious intent.                                                                              |
| **4719 — System audit policy was changed**                                                        | This event records changes to the audit policy on a computer. It could be a sign that someone is trying to cover their tracks by turning off auditing or changing what events get audited.                                                  |
| **4738 — A user account was changed**                                                             | This event records any changes made to user accounts, including changes to privileges, group memberships, and account settings. Unexpected account changes can be a sign of account takeover or insider threats.                            |
| **4771 — Kerberos pre-authentication failed**                                                     | This event is similar to 4625 (failed logon) but specifically for Kerberos authentication. An unusual amount of these logs could indicate an attacker attempting to brute force your Kerberos service.                                      |
| **4776 — The domain controller attempted to validate the credentials for an account**             | This event helps track both successful and failed attempts at credential validation by the domain controller. Multiple failures could suggest a brute-force attack.                                                                         |
| **5001 — Antivirus real-time protection configuration has changed**                               | This event indicates that the real-time protection settings of Defender have been modified. Unauthorized changes could indicate an attempt to disable or undermine the functionality of Defender.                                           |
| **5140 — A network share object was accessed**                                                    | This event is logged whenever a network share is accessed. This can be critical in identifying unauthorized access to network shares.                                                                                                       |
| **5142 — A network share object was added**                                                       | This event signifies the creation of a new network share. Unauthorized network shares could be used to exfiltrate data or spread malware across a network.                                                                                  |
| **5145 — A network share object was checked to see whether client can be granted desired access** | This event indicates that someone attempted to access a network share. Frequent checks of this sort might indicate a user or a malware trying to map out the network shares for future exploits.                                            |
| **5157 — The Windows Filtering Platform has blocked a connection**                                | This is logged when the Windows Filtering Platform blocks a connection attempt. This can be helpful for identifying malicious traffic on your network.                                                                                      |
| **7045 — A service was installed in the system**                                                  | A sudden appearance of unknown services might suggest malware installation, as many types of malware install themselves as services.                                                                                                        |

# 🎯 Key Takeaways

Remember, one of the key aspects of threat detection is having a good understanding of what is **"normal"** in our environment.

Anomalies that might indicate a threat in one environment could be normal behavior in another. Therefore, it's crucial to tune our monitoring and alerting systems to our environment to minimize false positives and make real threats easier to spot.

In addition, it's essential to have a **centralized log management solution** in place that can collect, parse, and alert on these events in real-time.

Regularly monitoring and reviewing these logs can help in the early detection and mitigation of threats.

Lastly, we need to make sure to **correlate these logs with other system and security logs** to get a more holistic view of security events in our environment.
